# مِهنتي — منصة توظيف مستقلة

منصة عربية RTL تربط العمال بأصحاب الأفران والمخابز والمطاعم.

## التقنية
- React 19 + Vite 6
- Supabase Auth + PostgreSQL + RLS + Realtime
- Leaflet + OpenStreetMap لعرض موقع العامل وصاحب العمل وموقع الوظيفة
- Netlify للنشر

## قاعدة البيانات
المشروع المرتبط هو Supabase **Mihnaty**. الجداول القديمة محفوظة ولم تُحذف. تعمل المنصة على جداول مستقلة بأسماء `mihnati_*`.

الجداول الأساسية:
- `mihnati_profiles`: ملفات العمال والحسابات التجارية وأرقام الهواتف.
- `mihnati_jobs`: إعلانات الوظائف وإحداثيات موقع العمل الاختيارية.
- `mihnati_bookings`: الحجز وموافقتا الطرفين والوصول وموافقات مشاركة الموقع.
- `mihnati_messages`: الدردشة.
- `mihnati_live_locations`: آخر إحداثية فقط لكل طرف ولكل حجز، دون إنشاء سجل مسارات تاريخي.
- `mihnati_notification_events`: سجل منع تكرار إشعار الوصول.

## تتبع الموقع الحي
- يبدأ فقط بعد اكتمال موافقة العامل وصاحب العمل على الحجز.
- يتطلب موافقة منفصلة وصريحة من كل طرف على مشاركة موقعه.
- لا تُعرض المواقع إلا لطرفي الحجز، مع RLS وسياسات تحقق من حالة الحجز والموافقتين.
- يتم تحديث آخر موقع فقط عبر RPC محمية، وتبث التغييرات عبر Supabase Realtime.
- إيقاف المشاركة يحذف آخر إحداثية لذلك الطرف.
- يستخدم المتصفح GPS عالي الدقة، مع إرسال تحديثات متباعدة لتقليل استهلاك البطارية والبيانات.
- إذا سجّل صاحب العمل إحداثيات منشأته عند نشر الوظيفة، يمكن للمنصة رصد اقتراب العامل ضمن 100 متر وتسجيل الوصول تلقائياً. إذا لم تُحدد الإحداثيات، يبقى تأكيد الوصول اليدوي متاحاً.
- التتبع يعتمد على إذن الموقع والإنترنت وبقاء صفحة المنصة نشطة. متصفحات Android قد توقف التحديث في الخلفية أو عند إغلاق الصفحة أو تفعيل توفير الطاقة؛ لا يوجد ضمان تتبع مستمر بعد إغلاق المتصفح.

## الحساب التجاري وأرقام الهواتف
- التسجيل يطلب رقم هاتف إلزامياً للعامل وصاحب العمل.
- يستطيع الحساب التجاري تحديث رقم هاتفه من صفحة «حسابي».
- عند وصول العامل، يرسل بوت Telegram إلى المحادثة الخاصة المحددة: رقم العامل، اسم العامل، رقم صاحب العمل، اسم صاحب العمل، واسم المخبز/الفرن/المطعم.

## الحجوزات والتواصل
- الحجز ذري وحصري؛ لا يستطيع عامل آخر حجز الوظيفة النشطة نفسها.
- موافقة كل طرف مستقلة؛ لا يتم الاتفاق إلا بعد موافقة الطرفين.
- الإلغاء يعيد الإعلان إلى متاح عندما تسمح حالة الحجز.
- الدردشة محصورة بطرفي الحجز.
- لا توجد محفظة أو بوابة دفع أو إيداع أو سحب أو تحقق دفع داخل التطبيق. أي تحويل مذكور في الواجهة يدوي وخارج التطبيق.

## إعداد محلي
1. Node.js 20 أو أحدث.
2. `npm install`.
3. إنشاء `.env` اعتماداً على `.env.example`.
4. إضافة `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`.
5. `npm run dev` ثم `npm run build`.

لا تستخدم `service_role` أو مفاتيح سرية داخل الواجهة أو أي متغير يبدأ بـ `VITE_`.

## إعداد Netlify
- Build command: `npm run build`
- Publish directory: `dist`
- أضف متغيري Supabase أعلاه ثم نفّذ Deploy جديداً.
- إعداد SPA redirect موجود في `netlify.toml`.

## Telegram
- Edge Function: `mihnati-telegram`، مع `verify_jwt=true`.
- السر المطلوب: `TELEGRAM_BOT_TOKEN` داخل Supabase Edge Functions Secrets فقط.
- المستلم محدد داخل وظيفة الخادم ولا يقبل رقم مستلم من العميل.
- لا تضع التوكن في GitHub أو الواجهة. إذا سبق كشفه، ألغِه من BotFather وأصدر بديلاً.

## ما يحتاج اختبار قبول فعلي
- التسجيل وتأكيد البريد والدخول للعامل والتاجر.
- نشر وظيفة بإحداثيات ومن دونها.
- الحجز الحصري ومحاولات الحجز المتزامنة.
- موافقة كل طرف والإلغاء وإعادة فتح الإعلان.
- موافقة مشاركة الموقع من الطرفين، الرفض، إيقاف المشاركة، انقطاع الشبكة، وظهور آخر تحديث.
- اختبار الاقتراب التلقائي ضمن 100 متر عند نشر وظيفة بإحداثيات صحيحة، واختبار الوصول اليدوي عند عدم وجودها.
- وصول رسالة Telegram فعلياً بأرقام الطرفين.
- اختبار Android Chrome مع الشاشة المفتوحة والخلفية وتوفير الطاقة.
- نجاح GitHub Actions وبناء Netlify ثم اختبار النشر العام.

لا تجمع رقم الهوية أو صور المستندات في هذه النسخة قبل بناء تدفق تحقق آمن ومشفّر.
